# 从 Pi 源码读懂 Agent Infra

假设你希望程序帮你完成一件事：“读懂项目里的配置，增加一个模型，检查配置能否生效。”普通脚本需要你提前写好每一步。这里的 Agent 会把任务和已有信息发给大模型，让模型提出下一步，再由程序执行。执行结果返回后，程序重新请求模型，直到得到回答或遇到停止条件。

大模型在这套系统中接收信息、产生输出。它在某次请求里提出“读取文件”，文件还没有因此被读取；程序必须找到读取工具，执行它，把文件内容作为结果送回去。Agent Runtime 就是负责这段反复交接的运行程序。Infra 是 infrastructure 的缩写，指支持它持续工作的基础设施：消息放在哪里、状态如何保存、进程退出怎么办、工具有什么权限，以及怎样判断任务完成得对不对。

## 从一个改配置任务开始

以下是帮助理解的任务例子，不代表仓库已经内置了一套自动修改、审阅和发布的完整工作流。

1. 你输入“增加模型，保留原配置”。程序把这句话与当前提示词、工具说明发给模型。这一次发出的信息就是模型本次能使用的上下文。
2. 模型暂时不知道配置内容，返回一个读取文件的请求。程序检查工具名与参数，然后实际读取文件。
3. 程序把读取结果加入对话，再次请求模型。这一次模型看到文件内容，才有依据提出修改。
4. 程序执行修改工具，保存工具结果，并继续让模型检查。如果还需要其他文件，循环会继续；没有继续条件时，本次运行结束。
5. 你之后补充“另一个模型也要加”。程序需要保存此前的交互，才能在新的请求里提供必要信息。这就引出了会话历史与上下文管理。

最简单的成功路径到这里就能讲清楚。后面的基础设施，是为了处理这条路径遇到的具体情况。

| 同一个任务遇到的情况 | 系统需要补上的能力 | 章节 |
| --- | --- | --- |
| 读了很多文件，全部内容放不进下一次请求 | 选择要发送的历史，生成摘要，保留继续工作所需信息 | 02 |
| 工具还没结束，你又输入“先别修改” | 保存新输入，并在合适的执行边界交给模型 | 03 |
| 想让另一个 Agent 审阅修改结果 | 创建子工作，明确谁负责它、何时等待它、如何收尾 | 04 |
| 程序运行半小时后退出 | 把下一步和任务进度写到持久存储，重开后据此继续 | 05 |
| 网络断了，或者操作迟迟不返回 | 判断重做哪一步、等待多久，以及重复执行是否会产生重复效果 | 06 |
| 另一个界面想显示这项任务的最新状态 | 给观察者完整起点，再连续同步后续变化 | 07 |
| 命令需要在另一台机器执行 | 选择执行后端，并由实际部署限制访问范围 | 08 |
| 工具由外部服务提供 | 建立连接、发现工具、把请求与返回值接入 Agent | 09 |
| 工具需要凭证，或者某些操作应被阻止 | 分别处理服务身份、动作许可和秘密保存 | 10 |
| 用户发现任务很慢 | 记录发生了什么、哪一步耗时、消耗多少 | 11 |
| 最后回复“完成”，配置却没生效 | 检查实际产物，并用可重复案例评估 | 12 |

这些能力有不同的作用对象。输入消息、模型对话、持久任务、运行进程、外部操作结果，不能只用一个“状态”概括。例如，保存了对话不代表保存了正在运行的命令；界面显示“运行中”也不代表它有权执行任务。后面的章节会在具体过程里区分这些对象。

Pi 的 Agent（代理运行时）会把消息交给模型。模型可以回复文本，也可以请求工具执行操作；Agent 循环负责运行模型、执行被允许的工具，再把工具结果放回下一次请求。Session（会话）保存一段连续交互，并在新请求前准备模型要看的历史。读“读配置、修改文件、运行命令”这类小任务时，可以先跟踪模型何时发起工具调用，再看工具结果怎样回到对话。

| 对象 | 在一次任务中的作用 |
| --- | --- |
| 模型 | 根据请求中的消息和工具声明，给出回复或提出工具调用 |
| 工具 | 读取文件、运行命令等具体操作；由 Agent 执行并返回结果 |
| Agent 循环 | 在模型请求、工具执行、结果写回和停止条件之间推进 |
| Session | 保存连续交互，管理历史、扩展和后续请求需要的上下文 |
| Agent Infra | 承接循环周边工作，例如队列、持久化、权限、执行环境、重试和观测 |

本目录的 12 篇文章从一次请求逐步延伸到任务调度、恢复和验证。每篇按自己的主题展开：先看文中例子与对象，再沿相应源码和测试确认实现。流程图放在解释过图中对象和路径之后，适合用来回看完整关系。

## 先分清两条运行路径

“运行路径”指程序实际经过的那组代码。Pi 有日常 CLI 路径，也有实验性的持久任务路径。CLI 是命令行界面，你在终端里输入任务并看到输出；持久任务路径则额外保存任务的执行阶段，研究进程重启后的继续执行。它们可以完成相似的模型与工具交互，但记录的状态、调度方式和恢复规则不同。

默认 CLI 用 `AgentSession` 组织模型调用、工具执行和会话记录。实验中的 durable harness 则把工作拆成可以持久保存的任务。两条路径共用了部分模型和工具代码，但执行引擎各有一套。读源码时，先认清自己正在跟哪条路径，后面的状态和恢复逻辑才容易对上。

例如，默认 CLI 重新打开 Session 时，会恢复已有对话；工具执行到一半、进程退出后该怎么办，则要去看 durable Scheduler 的策略。durable 中的工具恢复规则，也只在那条运行路径中生效。

`pi-durable` [明确标为 Experimental](../../packages/durable/README.md#L1-L7)。`coding-agent/src/experimental` 里的入口仍在实验阶段，`examples` 则是可以选用的扩展示例。这些代码确实存在，适合拿来学习；离完整的生产系统还有哪些距离，各篇会结合实现交代。

## 第一次读，可以沿着这条顺序

先读 01、09、02。跟着“prompt → model → tool → ToolResult → model”走完一次循环，再检查模型真正收到了哪些消息。工具调用和上下文放在一起看，比单独记住接口名称更容易理解。

接着读 03、05、06，追踪任务从等待到执行，再到结果落盘。把进程中断的位置分别放在提交意图之前、外部操作之后、保存结果之前，看看恢复时掌握的证据有什么不同。

04 和 07 把范围扩展到多个任务和进程：工作归谁、正在等谁，以及客户端拿到的是哪一份状态。这里还要分清观察状态的副本和真正拥有执行权的进程。

最后读 08、10、11、12。文件和命令在哪里运行，哪些动作会被允许，执行中留下了什么记录，产物又该怎样检查，这几件事会直接影响你对前面代码的理解。

读测试时，可以先看 mock/faux provider 和人工构造的状态，再看断言，最后按章节给出的命令跑指定用例。读源码和大部分单元测试都不需要真实模型。模型 eval、外部 SSH、容器和微虚拟机案例则需要另外准备环境。

## 再把这些问题放进同一个任务

试着设想这样一个任务：“主 Agent 调研配置格式，Worker 修改文件，Reviewer 检查，再等待人工决定是否发布。”读到相关章节时，可以拿下面的问题对照源码。它们分别落在哪个对象、哪次调用或哪条持久记录上？

| 要回答的问题 | 对应章节 |
| --- | --- |
| 何时触发下一轮模型调用，工具结果怎样回到模型？ | 01、09 |
| Worker 能看到哪些历史；压缩后仍保留哪些约束？ | 02 |
| 输入队列与待执行任务是谁管理的，并发如何产生？ | 03 |
| Reviewer 是子会话、扩展还是任务；人工决定在哪里接入？ | 04、10 |
| 改文件过程中进程崩溃，哪些状态保留、哪些工作会重跑？ | 05、06 |
| 两个进程读取同一 Session，谁拥有执行权，副本如何同步？ | 07 |
| 文件和命令在哪个环境执行，模型凭证是否进入该环境？ | 08、10 |
| 如何关联一次模型回复与对应工具，并统计真实成本？ | 11 |
| 如何验证文件或运行时真正改变，而非只检查最终回复？ | 12 |

这条完整工作流需要自己把现有机制接起来。练习时遇到项目尚未提供的部分，也可以顺着各篇对实现范围的说明，看看具体还缺哪一步。
