# Agent 基础设施教程

本教程面向初次学习 Agent 基础设施的读者，介绍模型参与任务执行时所需的运行机制。学习范围包括模型与工具的交互、上下文组织、任务调度、状态恢复、执行隔离，以及运行过程和结果的评估。Pi 是本教程的参考项目，用于说明这些机制的实现方式及其适用范围。

完成学习后，读者应能描述一项任务从接收到完成的执行过程，区分各类状态的保存位置，并分析任务积压、重复执行、进程故障和结果错误的处理方式。对于项目尚未提供的能力，教程先解释其设计原理，再说明现有实现与完整方案之间的差距。

## Agent 的运行过程与基础设施职责

Agent 是围绕任务目标反复调用模型和工具的程序。模型根据收到的信息生成回答或提出工具调用；运行时负责校验调用、执行工具、记录结果，并准备后续模型请求。工具可以读取文件、执行命令或访问外部服务。运行过程在满足结束条件、用户取消或执行预算耗尽时停止。

以修改项目配置为例，用户要求增加一个模型配置，同时保留原有配置并验证加载结果。程序首先将要求和可用工具提交给模型。模型提出读取文件后，运行时执行读取，并将结果纳入下一次请求。随后，模型根据文件内容提出修改，程序执行写入与加载检查。写入成功只说明一个操作完成；整项任务是否成功，还取决于修改是否符合约束、配置是否能够正常加载。

上下文是一次模型调用实际接收的信息。会话历史、磁盘文件和程序内存中的状态都需要经过选取与转换，才能成为上下文。Session（会话）组织多次相关交互，运行状态则记录当前模型、活动工具、取消标记和待处理输入。不同信息具有不同的保存与恢复要求。

Agent 基础设施进一步处理长期运行和并发执行中的问题。任务队列协调请求提交速度与执行容量；编排机制管理子任务依赖与产物交接；持久执行机制保存恢复依据；重试、幂等与分布式协调共同约束故障后的行为。执行环境和权限系统限制工具访问范围，可观测性与评估系统分别提供运行证据和质量判断。

## 一项任务中的机制协作

以批量修改多个项目配置为例，接收服务先确认请求者身份并检查项目访问权限，再将工作提交到任务队列。空闲 Worker 按调度规则领取任务，准备上下文并启动 Agent 循环。模型请求的文件读取、命令执行和网络访问，通过工具接口进入指定执行环境，并受权限与资源限制约束。

存在多个阶段时，编排层根据依赖关系安排调研、修改和审阅。独立任务可以并行执行；审阅以具体修改产物为输入；需要人工批准的操作在收到决定前保持等待。各阶段的输出、状态和责任归属共同决定后续任务是否可以开始。

执行过程中，系统保存已完成阶段和继续运行所需的数据。网络错误由重试策略处理，进程退出后则依据持久记录恢复。若外部操作已经成功，但结果尚未保存，恢复者需要通过幂等键或结果查询确认实际情况。多个执行者共同工作时，还需要协调任务领取、状态更新和执行权失效后的接管。

观测记录覆盖排队、模型调用、工具执行与重试过程，用于解释延迟、成本和故障原因。任务结束后，评估系统按照预先确定的标准检查产物，例如旧配置是否保留、新配置是否能够加载。运行过程完整与任务结果正确是需要分别验证的两个方面。

上述流程是通用教学设计。Pi 中不同模块和示例分别覆盖其中部分机制，不能据此推定默认安装包含完整的服务端任务系统。

## 章节之间的关系

检查点同时涉及第 2 章和第 5 章。第 2 章关注后续请求需要的信息及其保存形式，第 5 章关注进程退出后恢复执行所需的依据。自然语言摘要与结构化任务检查点具有不同的精度和保证范围。

恢复依赖一致的持久记录，因此第 5 章需要用到第 7 章的事务与存储知识。事务可以将同一存储中的相关修改一起提交；项目文件和外部服务通常不在这一提交范围内，还需要第 6 章的幂等与结果核验机制。

重试既影响正确性，也影响资源消耗。第 6 章分析重试条件与重复效果，第 11 章记录重试次数、延迟和成本，第 12 章检查重试后的产物是否满足任务要求。执行追踪用于解释某次运行，评估则在明确的数据集和评分标准下比较运行结果。

## 阅读与实践建议

初次阅读可按以下顺序建立知识基础：

1. 第 1、9、2 章：理解最小 Agent 循环、工具接口和上下文组织。能够描述一次工具调用的提出、执行、结果保存与后续请求过程。
2. 第 8、10 章：理解执行环境、权限与凭据。能够确定一条命令的执行位置、访问范围、授权依据和资源限制。
3. 第 3、4 章：理解多任务调度与编排。能够区分容量不足、依赖未满足和等待人工决定三种等待状态。
4. 第 5、6、7 章：分析故障与恢复。分别在操作开始前、外部效果发生后、结果保存后中断流程，推导可恢复的状态和仍然未知的事实。
5. 第 11、12 章：建立诊断与评估方法。利用运行记录定位问题，再通过固定案例检查改动效果。

源码阅读可放在概念学习之后。先核对成功路径，再检查相关状态与失败分支，最后阅读测试的输入构造和结果断言。案例迁移也有助于检查理解：将配置修改换成研究报告生成，队列、超时与检查点仍然适用，但工具副作用和评分依据需要重新确定。

## Pi 参考实现的范围

Pi 的默认 CLI 使用 `AgentSession` 组织模型调用、工具执行与会话记录。实验 durable harness 将工作组织成可持久保存的任务，用于调度与恢复。两条路径共用部分模型与工具能力，但执行引擎、状态记录和恢复规则不同。普通会话重开主要恢复已有对话，持久任务恢复还需要重建未完成工作的执行状态。

`pi-durable` [明确标为 Experimental](https://github.com/earendil-works/pi/blob/96abe9a5ad45005cae34ed1c52d42f71fc88bedc/packages/durable/README.md#L1-L7)。`coding-agent/src/experimental` 现仅保留 `source-resolver.ts`（在源码运行时解析工作区别名），此前的 session worker 与服务端入口已随 `packages/client`、`packages/protocol`、`packages/server` 一并移除。`examples` 提供可选扩展示例，需要经过相应配置才能接入应用。

| --- | --- |
| 运行循环、上下文与工具 | 包含模型调用、工具执行、流式事件、历史投影和压缩实现；通用长期记忆检索仍需额外设计 |

| 观测与评估 | 包含事件、用量、成本、遥测接口及评估案例；完整自动追踪、指标后端和导出仍需接入；结果判定方式应按产物选择 |

源码材料以 Pi 提交 `96abe9a5ad45005cae34ed1c52d42f71fc88bedc` 为基线。阅读其他版本时，应重新核对实现与行号。本次修订将 durable 睡眠与唤醒、崩溃循环保护、SQLite schema 迁移、chord 宿主运行时、环境 PTY 与文件列举等新增内容对照提交 `482c1381a` 补充，其余章节的行号仍按基线理解。本地阅读版使用源码相对路径，GitHub 发布版使用固定提交的源码链接；两种版本的正文与图示保持一致。

在 Pi 仓库中，可从 `docs/agent-infra/README.md` 开始阅读。独立文档仓库的本地阅读分支为 `local-vscode`，要求它与 `pi` 源码目录位于同一个父目录；远程 `main` 为 GitHub 发布版。章节中的测试命令需要在 Pi 源码仓库的指定目录执行。实际模型评估、SSH、容器和微虚拟机案例还需要相应执行环境。
